# How to use the data-lineage map

A field guide for the three jobs the map exists to do. Each recipe
gives you the exact commands to run and a worked example.

The map has three artifacts:

- `lineage/<event>.yaml` — the per-event records (Phase 2). Source of
  truth; everything else is generated.
- `inverse-index.yaml` — `<table>.<column>` → `written_by` /
  `read_by` event lists, plus per-UI-page event lists (Phase 3).
  Generated by `build_inverse_index.py`.
- `diagrams/<event>.mmd` and `diagrams/_overview.mmd` — Mermaid
  graphs (Phase 4). Generated by `build_diagrams.py`.

Always reach for the inverse index first — text search is faster than
opening diagrams. Use the diagrams to confirm a chain visually once
you've narrowed the suspects.

---

## Recipe 1 — A UI metric looks wrong ("Cash Flow income is off")

You see a number on a page that disagrees with intuition. You want to
list every event that could be feeding it, then narrow to the
suspect.

1. **Identify the column.** Income on Cash Flow comes from the
   `income_cents` field of `dal/flow_aggregation.py:compute_period_totals`,
   which aggregates `transactions.signed_amount` filtered by category
   and `transfer_tag`. (If you don't already know the column, grep
   the page's component for `useQuery` or the `via:` fields in the
   relevant `lineage/*.yaml` `ui_surfaces` blocks.)

2. **Pull every writer + reader of that column.** Open
   [`inverse-index.yaml`](inverse-index.yaml) and jump to
   `transactions.signed_amount`. You get two lists:

   - `written_by:` — every event that creates a row with that
     column populated. For income, this is every transaction-shape
     event (`paycheck`, `bonus_or_one_off_income`, `tax_refund`,
     `purchase_refund`, …).
   - `read_by:` — every aggregator. Anything reading
     `transactions.signed_amount` is a candidate "wrong number"
     source.

3. **Filter by hypothesis.** If the suspect is "refunds inflating
   income," focus on the writers that produce `signed_amount > 0` but
   shouldn't count as income: `purchase_refund`, `cashback_redemption`,
   `tax_refund`, `reimbursement`. Open
   [`lineage/purchase_refund.yaml`](lineage/purchase_refund.yaml) — the
   `notes` block and the
   `INCOME_EXCL_FROM_INC` exclusion explain why it's already filtered
   out, and `tests/test_cashflow_invariants.py` is the regression
   guard.

4. **Visualize the chain.** Open
   [`diagrams/purchase_refund.mmd`](diagrams/purchase_refund.mmd) (paste
   into <https://mermaid.live> or use a VS Code Mermaid preview
   extension). You see origin → `transactions` → consumers /
   derivations → UI surfaces in one picture; the `external_effects`
   circle confirms what fires (e.g. `notification`).

5. **If the chain doesn't explain the bug,** the issue is upstream of
   the lineage map — usually a parser or seeder bug producing a row
   with the wrong category or sign. Open
   [`origin.file`](lineage/purchase_refund.yaml) for the writer to
   trace from there.

## Recipe 2 — "Can I delete `dal/X.py:foo()`?"

You're about to remove a function. You want to know if anything
analytical or UI depends on it before you do.

1. **Grep the lineage records.** The map cites every consumer +
   derivation by `file:symbol`. From the repo root:

   ```
   grep -rn "foo" docs/data-lineage/lineage/
   ```

   Every match in a `direct_consumers[].symbol` or
   `derivations[].symbol` is a current consumer **as of the most
   recent lineage edit**.

2. **Zero matches = likely dead.** Verify with `git grep` against the
   actual code — the lineage map is text, not runtime, and citations
   can drift. If both grep results are empty, you can delete with
   confidence.

3. **Matches exist — pull the blast radius.** For each event that
   cites the function, open `lineage/<event>.yaml` and read the
   `derivations[].fan_out` and `ui_surfaces` blocks. That's what
   you'll break if you remove the function without a replacement.

4. **Worked example: `dal.derived.recompute.recompute_interest_earned`.**
   Grep finds exactly one citation —
   [`lineage/interest_earned_recompute.yaml`](lineage/interest_earned_recompute.yaml).
   Read its `notes`: the writer is dead in synthetic mode (AI-019
   resolved 2026-04-26), the `derived_summaries` row is
   unconsumed by the UI, and the function is a deprecation
   candidate. The lineage map made that decision a 30-second
   exercise instead of a fishing expedition through `dal/`.

## Recipe 3 — PR review touching a central path

You're reviewing a PR that changes
`dal/transactions.py:upsert_transactions` (or the post-commit
pipeline, or any analytical aggregator). You want to articulate
"here's what this affects" without reading every page component.

1. **Find the lineage record for the entry point.** For
   `upsert_transactions`, that's
   [`lineage/sign_direction_invariant.yaml`](lineage/sign_direction_invariant.yaml).
   It documents the choke-point invariant and the fact that **every**
   transaction-shape event flows through it.

2. **Pull the full call set.**

   ```
   grep -l "upsert_transactions" docs/data-lineage/lineage/*.yaml
   ```

   Almost every event that writes the `transactions` table shows up
   — that's the change's blast radius.

3. **Visualize the system-level shape.** Open
   [`diagrams/_overview.mmd`](diagrams/_overview.mmd). You can see at
   a glance that all four event classes flow into `transactions`,
   which fans out to Cash Flow, Transactions, Reports, Dashboard,
   Budgets — i.e. every primary surface. Any change to the choke
   point needs eyes on all of them.

4. **Spot-check by class.** Pick one diagram per event class to
   sanity-check the chain still makes sense after the PR's logic:

   - `user_action`: [`diagrams/paycheck.mmd`](diagrams/paycheck.mmd)
     or [`diagrams/retail_purchase.mmd`](diagrams/retail_purchase.mmd)
   - `external_force`: [`diagrams/bank_interest_credit.mmd`](diagrams/bank_interest_credit.mmd)
   - `live_only`: [`diagrams/connector_transactions_csv_upsert.mmd`](diagrams/connector_transactions_csv_upsert.mmd)
   - `system_derived`: [`diagrams/auto_categorization.mmd`](diagrams/auto_categorization.mmd)

5. **Ask in the PR review:** does the change preserve the canonical
   filter pattern (`signed_amount` + `transfer_tag IS NULL` +
   category exclusion sets)? `CLAUDE.md > Non-Negotiable Guardrails`
   has the rule; the lineage map shows what breaks if you violate it.

## Keeping the map honest

The map is generated; it only stays accurate if regenerated after
every lineage YAML edit. Two safeguards:

- **Pre-commit hook** — `scripts/install_hooks.sh` registers a
  pre-commit hook that runs the lineage freshness check whenever a
  `docs/data-lineage/lineage/*.yaml` is staged. If the index or any
  diagram would change, the hook regenerates the artifacts, prints
  which files moved, and exits non-zero so the commit blocks. Install
  once per clone:

  ```
  bash scripts/install_hooks.sh
  ```

- **Manual regeneration** from `docs/data-lineage/` (anytime, not
  just at commit):

  ```
  python build_inverse_index.py
  python build_diagrams.py
  ```

- **One-shot freshness check** — same code path the hook uses, runnable
  on demand:

  ```
  python docs/data-lineage/check_freshness.py
  ```

  Exit code 0 ⇒ index + diagrams already match; exit code 1 ⇒
  regenerated files are now in your working tree (re-stage and
  re-commit, or revert if your YAML edit was unintentional).

If you edit a `lineage/*.yaml` and skip regeneration, the index and
diagrams silently drift from the YAML. The pre-commit hook is the
backstop.

## When NOT to consult the map

- Quick code-only questions (file/symbol lookups). `git grep` /
  Glob / Grep are faster.
- Questions about *runtime* behavior (timing, ordering, error
  states). The map is static; read the code or run the seeder
  with logging.
- Questions the architecture doc already answers
  (`docs/ARCHITECTURE.md` §3 process model, §4 data architecture).

The map shines at "fan-out" questions — given an event or column,
what depends on it. For "fan-in" questions about a single
function's internals, read the function.
